# Tag 发布 Release

只做版本准备、更新说明、推送 Tag 和核对 Release。读取当前仓库的项目名、版本来源和 `.github/workflows/` 下的 Tag 发布工作流，使用已有流程，不绑定项目、语言或框架。缺少 Tag 发布流程时说明缺口，不擅自扩展为 CI 搭建任务。

## 先确定项目支持范围

在修改构建矩阵、执行打包或推送发布 Tag 前，先读取项目的平台说明、关键平台适配代码、打包配置和现有发布工作流，确定本次要发布的系统、架构和包类型。

- 默认逐项核对 Windows、macOS、Linux × x64、ARM64 共六种组合，发布其中项目实际支持的全部组合；用户明确限定范围时，取该范围与实际支持范围的交集。不支持的组合不构建、不发布，并简要说明缺失原因。
- 不能仅沿用已有 CI 矩阵或历史附件而漏发项目已支持的组合。已有代码与关键依赖支持、但缺少打包配置的组合，应在发布前补齐必要的最小构建与上传配置；若仍需移植核心功能或替换不兼容依赖，则属于尚未支持，不能靠增加矩阵项或改名冒充支持。
- CI 中存在某个平台、框架支持跨平台、历史 Release 曾有某个包，都不能单独证明项目支持该平台。检查启动、核心功能、系统集成及关键依赖是否有对应实现；操作系统支持不自动代表它的所有架构都受支持。
- 区分“已有实现”“构建通过”“实机验证”。缺少实机验证不自动取消已有的平台支持，但必须如实说明；发现关键能力未实现或支持声明冲突时，先查明，不为凑齐平台临时扩展产品能力。
- 简要向用户说明本次发布范围和依据，再按该范围准备清单。范围明确且已有发布授权时直接继续；仅在事实无法确定且会影响范围时询问。

## 最小发布清单

- 默认 Tag：`vX.Y.Z`；Release 标题：`<项目名> vX.Y.Z`；附件中的版本号不带 `v`。项目有明确版本规范时沿用。
- 全部六种组合均支持时，默认发布六个分架构的主要下载包；只支持 Windows/macOS 双架构时发布四个；其他情况只发布支持的子集。附件总数另外计入确有用途的便携包、自动更新文件和校验文件，不能把安装版与便携版当作两种架构。
- 先列出本次 Release 的附件白名单，逐项写明文件名、系统/架构、用途及支持依据，并分别统计用户下载包、自动更新文件、校验文件的数量。
- 默认每种已支持组合单独出包。macOS 同时支持 Intel 和 Apple Silicon 时，分别提供 x64 DMG 与 ARM64 DMG，不能仅以一个 Universal DMG 代替这两个下载包。只有用户明确要求或已有更新器确实依赖时才保留 Universal；用户明确要求仅提供 Universal 时遵循用户选择。分架构包内的运行时和原生依赖也必须匹配目标架构。
- 用户下载包按每个已选系统/架构选择一种主要分发格式。免安装包、第二种安装格式或额外归档仅在用户要求或项目有明确分发需求时增加；不能因为打包工具能生成就全部发布。
- 下表是桌面应用的默认候选矩阵，仅将实际支持的行加入发布清单。`x64` 与 `amd64` 是同一架构，不重复出包；库、CLI 等项目使用自身分发形式，并核对适用的组合。

| 系统／架构 | 主要下载包示例 | 格式说明 |
|---|---|---|
| Windows x64 | `<项目名>-X.Y.Z-windows-x64-setup.exe` | 需要免安装分发时另加便携包 |
| Windows ARM64 | `<项目名>-X.Y.Z-windows-arm64-setup.exe` | 须有原生 ARM64 支持，x64 模拟运行不算原生版本 |
| macOS x64 | `<项目名>-X.Y.Z-macos-x64.dmg` | Intel Mac |
| macOS ARM64 | `<项目名>-X.Y.Z-macos-arm64.dmg` | Apple Silicon Mac |
| Linux x64 | `<项目名>-X.Y.Z-linux-amd64.deb` | 按支持的发行版选择 `.deb`、`.rpm` 或 AppImage |
| Linux ARM64 | `<项目名>-X.Y.Z-linux-arm64.deb` | 按支持的发行版选择 `.deb`、`.rpm` 或 AppImage |

### 自动更新文件与构建中间产物

- 自动更新可能需要额外归档、签名或清单。检查现行更新器及项目明确维护的旧客户端通道，为每个保留文件指出实际消费者或清单引用；不能以“可能兼容旧版”为由无限保留。
- 必需的更新文件加入同一附件白名单，在 Release 说明中单列“自动更新使用，无需手动下载”。它们不算另一套用户下载版本，但必须计入附件总数；同一文件兼作安装包和更新载荷时只发布一份。
- 构建时必需的 `.app`、临时目录、调试符号和中间归档不自动成为 Release 附件。某格式若仅用于生成更新载荷，可以构建，但只上传清单中真正需要的文件。
- 检查工作流的构建参数和上传规则，避免 `--bundles all` 或无筛选的通配符把无用途的包全部上传。根据已确定清单作必要的最小调整，不借此重设计 CI。
- 保留有明确用途的现有命名，避免改名破坏更新 URL。添加覆盖所有用户下载包的 `SHA256SUMS`；如同时校验更新载荷，明确列出范围。GitHub 自动提供的源码压缩包不计入上传附件。

发布清单示例：项目只支持 Windows x64，用户仅需安装版，则主要下载包只有一个 setup.exe；如更新器确实需要，再增加该安装包的签名和更新清单，以及校验文件。不能据此增加 ARM64、macOS、Linux 或免安装版。

## 执行流程

1. 确认用户要求的版本、发布提交及远端；未指定提交时使用当前分支已确认的待发布内容。检查工作区、远端分支和同名 Tag/Release。逐项核对六种候选组合、支持依据和附件白名单，补齐已支持但漏配的目标，确认工作流只构建必要目标、只上传列明附件。现有流程多发的包也要检查用途，不能直接当成本次要求。发现无关改动或版本不明时，只澄清该问题。
2. 找到项目实际使用的版本来源，核对与目标版本一致；需要时只更新对应版本声明。根据上一次已发布版本到本次提交的实际差异，编写简洁中文更新说明，沿用项目更新日志位置，没有约定则保存到 `docs/releases/vX.Y.Z.md`。列出新增、修复、调整中的适用项，空项省略；首次发布概述现有功能，不虚构历史对比；不把未运行的测试写成通过。下载指南只列白名单中的用户下载包，说明适用平台、架构和必要的验证边界；自动更新文件另作说明。
3. 将版本号、更新说明及用户已授权发布的代码提交到目标分支并推送。发布请求已明确授权时直接继续，不重复询问；仅讨论或起草发布方案不视为推送授权。
4. 在准确的发布提交上创建附注 Tag：`git tag -a vX.Y.Z <commit> -m "<项目名> vX.Y.Z"`，然后 `git push origin vX.Y.Z`，由现有 Actions 创建 Release。替换示例中的版本、项目名、提交和远端；不要推送全部标签，不覆盖或移动已有标签。
5. 等待该 Tag 对应的构建和发布任务完成。工作流使用自动生成说明时，通过 `gh release edit vX.Y.Z --notes-file <本次更新说明文件>` 将已准备的中文更新内容写入 Release；已有综合 CHANGELOG 时只提取本版本内容。保留正确的标题和附件，始终用文件传递多行说明。
6. 核对 Release 的 Tag/提交、标题、中文更新内容。将实际上传附件与白名单逐项比较，同时检查缺失、多余、重名别名和错误平台，不能仅以“所需文件都在”判定合格。核对 `SHA256SUMS` 的覆盖范围，以及更新清单引用、版本和签名。全部符合后返回 Release 链接、实际支持范围和发布结果。

## 边界

- 不因发布额外启动本地全量测试或本地打包；遵循项目要求并让现有 CI 执行其检查。
- 构建失败、附件缺失、多发无用途附件或校验清单不完整时，不宣称发布完成。先定位并说明差异，在已有授权范围内准备最小修正；不能为了绕过失败临时增删支持平台，也不通过连续递增版本试错。
- 发布前可按已确定的支持范围和白名单调整构建、上传规则；发布后删除附件、覆盖或移动 Tag、删除 Release 需要明确授权。不能为缩减附件数破坏仍在使用的自动更新链路。
- 已有同名 Tag/Release 时先核对是否为同一提交和一次未完成发布；一致则续接核对/补写说明，不一致则停止该版本发布并说明冲突。
